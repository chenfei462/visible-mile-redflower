# 合成可读性设计

## 目标

让玩家在不打开额外面板、不记配方、不靠试错的前提下，直接从卡面和桌面反馈看懂：

- 这张卡现在能和谁合成
- 合成后会变成什么
- 桌面上哪几张是当前可配对的牌

## 问题总结

当前项目里已经存在部分配方提示，但它们没有出现在玩家真正做决定的地方：

- `PlayabilityDirector.get_recipe_hints()` 只在 tooltip / 额外文本里生成短句。
- `MainView._card_playability_text()` 只把提示塞进卡片附加文本，没有把它变成卡面主信息。
- 现有提示可见牌源主要来自 `hand_cards`、`bulletin_cards`、`craft_slots`，没有把桌面主操作区作为第一信息面。
- 玩家最需要的“桌面上哪两张现在能配”并没有通过显眼高亮或配对联动直接表现出来。

结果就是：逻辑在、数据在、提示也部分存在，但玩家感知到的仍然是“乱”和“靠猜”。

## 设计结论

采用“双层直觉提示”：

1. 卡面直说
2. 桌面联动高亮

配方手册、tooltip、快速合成按钮继续保留，但降级为补充信息，不再承担主教学职责。

## 方案对比

### 方案 A：卡面直说 + 桌面联动高亮

优点：

- 最贴合当前诉求，玩家不用记忆和试错。
- 玩家在主要操作区域就能看到答案。
- 可以复用现有配方提示逻辑，不需要重做配方系统。

缺点：

- 卡面信息密度会上升，需要控制文案长度。

### 方案 B：只在悬停时显示配对关系

优点：

- 卡面更干净。

缺点：

- 玩家仍然需要一张张试着悬停。
- 首次上手依然会觉得乱。

### 方案 C：新增固定“当前可合成配方”面板

优点：

- 信息完整。

缺点：

- 仍然是额外面板。
- 不符合“直接看桌面就懂”的目标。

### 推荐

选方案 A，并加入轻量的悬停/选中联动作为辅助。

## 交互设计

### 1. 卡面合成提示

当一张卡当前存在可见配对卡时，在卡面正面正文区增加一行短提示：

- 单一配对：
  - `可与 木料包 合成 -> 社区坡道`
- 多个配对：
  - `可与 木料包 合成 -> 社区坡道`
  - 第二行短补充：`另有 1 种可合成`

规则：

- 只展示“当前可见且已解锁”的配对，不展示未来配方。
- 优先展示当前最直接、最可完成的配方。
- 文案必须短，不使用长句解释。

### 2. 桌面联动高亮

当玩家悬停或选中一张有可配对关系的卡时：

- 所有可配对的搭档卡发亮。
- 当前卡保持主高亮。
- 无关卡轻微变暗，但不完全隐藏。
- 如果只有一个结果，可以在当前卡或顶部提示区同步显示结果名。

目标是让玩家一眼看见“这张卡该去找谁”。

### 3. 无配方状态

如果当前没有任何可见搭档：

- 不显示误导性的合成提示。
- 保留现有基础说明，例如材料/许可用途或开包引导。

## 实现边界

### 数据来源

复用现有配方数据，不新增 JSON 结构。

核心变化是把“可见配对判断”变成一个可复用的主逻辑，统一服务于：

- 卡面正文提示
- 卡片高亮状态
- 桌面联动高亮
- 快速合成按钮

### 可见牌范围

本次把这些区域都视为“当前玩家能直接看到并理解的牌”：

- 桌面卡
- 手牌 / 配方手册中的牌
- 合成区中的牌
- 公告栏中的牌

这样可以避免“明明桌上就有搭档卡，但系统提示看不见”的断层。

### 取舍规则

如果一张卡命中多个可见配方：

- 卡面默认显示第一优先配方。
- 其他可行配方只用数量补充，不在第一版把整张卡面塞满。

优先级规则：

1. 当前两张牌都已经可见
2. 结果是设施时优先于普通材料结果
3. 开局教学链路相关设施优先

## 代码设计

### `PlayabilityDirector.gd`

把当前只返回字符串提示的配方辅助逻辑升级为结构化结果，至少能提供：

- `partner_card_id`
- `result_card_id`
- `result_name`
- `partner_name`
- 是否为设施结果

保留原有字符串接口，避免一次性改太多调用点。

### `MainView.gd`

新增一层统一的“可见配方匹配结果”整理逻辑，用于：

- 给 `CardView.configure()` 传入卡面合成提示
- 判断哪些卡需要高亮
- 在悬停 / 选中时计算匹配卡实例集合

关键要求：

- 桌面卡必须进入匹配源
- 不再只靠 tooltip 传递配方信息

### `CardView.gd`

在卡片正面增加专门的合成提示展示位，而不是把提示混进现有长正文里。

要求：

- 提示文字短、对比度高
- 多配方时显示“另有 N 种”
- 被联动高亮时，视觉上要明显强于普通边框高亮

## 错误处理

- 如果配方数据缺失或结果卡不存在，卡面不显示坏文案，直接回退为无提示。
- 如果一张卡有高亮状态但配对实例在当前刷新周期消失，下一次 UI 刷新应自动清除，不保留脏状态。

## 测试策略

先写失败测试，再改实现。

至少补这几类回归：

1. 配方提示来源包含桌面卡，而不只包含手牌/公告栏。
2. 当前卡存在桌面可见搭档时，卡面提示文本明确包含“搭档名 -> 结果名”。
3. 当前卡存在多个可见配方时，卡面只显示主配方并带“另有 N 种”补充。
4. 悬停或选中一张可合成卡时，匹配搭档卡被标记为联动高亮，无关卡被标记为变暗。
5. 无可见搭档时，不应出现误导性的可合成提示。

## 范围外

- 不重做整个配方手册
- 不新增复杂筛选面板
- 不修改配方平衡或卡牌解锁顺序
- 不做全量 UI 视觉重构
