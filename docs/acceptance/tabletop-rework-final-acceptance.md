# 小红花社区桌面玩法改造最终验收清单

用于验收“小红花社区”从旧网格玩法改造成参考图片/视频风格的自由堆叠卡牌桌面玩法。验收时不要只看“能运行”，要逐项确认视觉、交互、规则、旧系统清理和自动化结果。

## 1. 参考图相似度

- [ ] 主界面整体接近参考图：浅绿色手绘草地桌面，而不是旧网格棋盘。
- [ ] 画面有手绘树木、草丛、纸张质感、粗黑描边等参考风格。
- [ ] 中央是大面积自由桌面区域，卡牌可以散落摆放。
- [ ] 卡牌可以自由拖拽、重叠、堆叠。
- [ ] 卡牌堆叠时能露出上方标题条，像参考图中的堆牌效果。
- [ ] 顶部有黑色公告栏/商店卡槽。
- [ ] 左侧有纸质任务/意图列表。
- [ ] 右上角有资源、日期、时间推进入口。
- [ ] 底部有缩放、整理、设置等工具按钮或等价操作入口。

## 2. 公告栏规则

- [ ] 每天公告栏固定刷新 5 张卡。
- [ ] 每天正好包含 2 张 `building_permit`。
- [ ] 每天正好包含 3 张 `material`。
- [ ] 公告栏不会出现建筑成品卡。
- [ ] 公告栏不会出现 `support` 支援卡。
- [ ] 公告栏不会出现 `problem` 问题卡。
- [ ] 公告栏不会出现居民卡。
- [ ] 公告栏卡池只允许 `material` 和 `building_permit`。

## 3. 建筑合成规则

- [ ] 所有建筑都通过“建筑许可 + 1 份专属材料”直接完成。
- [ ] 合成成功后直接得到建筑卡/建筑实体。
- [ ] 不存在旧升级链配方。
- [ ] 不存在旧兼容入口配方。
- [ ] 不存在 `support` 结果配方。
- [ ] 不需要多阶段升级才能得到基础建筑。

## 4. 居民需求交互

- [ ] 每天白天开始时，居民需求已经可见。
- [ ] 每个居民至少生成 1 个当天需求实体/需求卡。
- [ ] 需求卡能被玩家看到，不只是在黄昏结算文案里出现。
- [ ] 需求可以通过玩家交互解决。
- [ ] 玩家能清楚知道需求需要哪类服务建筑。
- [ ] 服务建筑能解决匹配需求。
- [ ] 服务建筑显示或体现容量限制。
- [ ] 黄昏只惩罚未解决需求。
- [ ] 需求交互不会卡死流程。

## 5. 建筑产出规则

- [ ] 建筑不再自然产出资源。
- [ ] 绿化建筑没有居民驻扎时不产小红花。
- [ ] 绿化建筑有居民驻扎时才产小红花。
- [ ] 商业建筑没有居民驻扎时不产资金。
- [ ] 商业建筑有居民驻扎时才产资金。
- [ ] 服务建筑不通过驻扎产出小红花。
- [ ] 服务建筑不通过驻扎产出资金。
- [ ] 服务建筑只负责居民需求处理。

## 6. 住宅、志愿者与迁入

- [ ] 住宅仍通过公告栏许可体系获得。
- [ ] 住宅许可消耗资金。
- [ ] 住宅首档价格为 `2`。
- [ ] 住宅每次购买后下一档价格 `+2`。
- [ ] 志愿者站仍通过公告栏许可体系获得。
- [ ] 志愿者站许可消耗小红花。
- [ ] 志愿者站首档价格为 `2`。
- [ ] 志愿者站每次购买后下一档价格 `+2`。
- [ ] 每 5 天按住宅上限检查迁入。
- [ ] 当前居民数低于住宅上限时会补满迁入。
- [ ] 新居民使用现有 `residents.json` 人设循环生成。
- [ ] 新居民有编号扩展，`resident_id` 不冲突。

## 7. 旧系统断开

- [ ] 主循环不再依赖 `problem` 旧问题系统。
- [ ] 主循环不再依赖 `trust` 信任解锁系统。
- [ ] 主循环不再依赖 `autonomy` 自治系统。
- [ ] 主循环不再依赖 `support` 支援卡玩法。
- [ ] 今日目标不再出现旧 `problem` 目标。
- [ ] 今日目标不再出现旧 `wish` 目标。
- [ ] 旧网格不再是主建筑放置方式。
- [ ] 旧字段存在于存档时不会导致崩溃。
- [ ] 旧字段缺失时新流程也能正常运行。
